  The one that shapes the whole architecture: 2 ch × 10 MSPS × 12 b = 240 Mb/s.

  Cost is roughly turns × context size. 174M of the 181M tokens were cache
  reads; output was under 1M. So there are three levers: fewer turns, less
  context per turn, and fewer wasted runs.

  Recommendations

  1. Stop losing paid work to failed runs. This is the biggest item. The block
  coders spent $22 and delivered 4 of 9 files; the librarian took 3 runs and 82
  minutes.
  - Cap block-coder concurrency at around 3. A 9-way Opus burst hit the spend
    limit all at once, and every coder died together.
  - Put "write the handoff skeleton first, save each artifact as you go" into
    every agent definition. That instruction is the only reason the librarian's
    work survived.
  - Add a driver rule: never resume an agent whose context is exhausted. The
    signature is the same result text and ~200k tokens on every resume. Start a
    fresh agent with a narrower scope instead.

  2. Replace both LLM-backed hooks with scripts. Cheap to do, and it affects
  every call.
  - The PreToolUse prompt hook runs a model call before every Bash command, 710
    times this session. It also treated creating a new file as an overwrite. A
    ~30-line script can block rm/mv/>/sed -i on protected dirs, and only when
    the target already exists. That's instant and deterministic.
  - The Stop agent hook starts a full agent every time the main thread stops.
    The same check works as a script: session-start.sh touches a marker file,
    the Stop script runs find circuits -newer marker plus a jq read of
    pipeline_state.json.
  - Caveat: hook model usage isn't in the transcripts, so it's not in the $125,
    and I can't measure its cost. The added latency on every call is certain.

  3. Move lookup work into scripts.
  - Sourcing: the sourcer made 55 calls over 53 minutes, running curl one part
    at a time. A source-bom.py could query every MPN in one pass. Connecting the
    pcbparts MCP would also help (it was missing).
  - Datasheets: five "PDFs" were really HTML error pages, and the agent spent
    turns finding that out. A fetch wrapper that checks file -b for a real PDF
    prevents this.
  - Symbols: three keystone symbols (AD9235, GW1NR-9, AD8066) don't exist in the
    KiCad libraries. That wasn't found until coding, and a block coder died
    generating one. Check symbol availability during sourcing and generate
    missing ones with kipart before coding starts.
  - Pin tables: my parser got the GW1NR-9 bank map in about 6 calls. The
    librarian spent far more and still reported 71 I/O instead of 48. A reusable
    pin-table-to-CSV extractor could feed both symbol generation and a
    bank-budget check.

  4. Shrink context per turn. Each turn re-reads 54–121k tokens.
  - Tell agents to batch independent reads into one call.
  - Read PDFs with pages= instead of converting whole datasheets to text.
  - Enforce the ~150-line handoff limit the rules already state.

  5. Right-size the coding fan-out. The ">3 blocks → modular" rule started 9
  Opus agents, including trivial ones like aux_io (3 parts). Each agent pays a
  fixed cost to read the rules and handoffs, and several died during that
  read-in.
  - Group small blocks into 3–4 coder runs.
  - Possibly run power and connector blocks on Sonnet, keeping Opus for the
    analog front end, FPGA, and review. Treat that as something to test: the
    filter bug shows analog work needs the strongest model.

  6. Cache datasheet summaries and symbols across projects, keyed by MPN. This
  is the third dual-ADC design in this tree, and the AD9235, FX2LP, and THS4551
  work was redone from scratch each time. The cache needs an off switch, because
  your blank-slate test protocol correctly forbids reuse.

  Don't cut the ERC reviewer. At $15 it found both HIGH defects, one of them
  mine, and was the best money spent all run. Giving it a checklist (filter
  topology, absolute-max levels, bank voltages) would cut the context it spends
  working out where to look.

  The failure-related waste is specific to hitting the spend limit, so expect
  items 2–5 to be the lasting savings on normal runs. Items 1 and 2 are the
  quickest to implement. Want me to draft the two hook scripts in the plugin
  repo? I'd edit the working tree only and leave the commits to you.
